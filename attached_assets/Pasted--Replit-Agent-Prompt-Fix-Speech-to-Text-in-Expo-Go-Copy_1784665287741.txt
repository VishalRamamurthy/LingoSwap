## Step 1 — Diagnose before changing anything

Trace the full STT path end to end: mic permission request → `expo-av` recording setup → recording file (URI, format, size) → upload to the backend → backend transcription call → response back to the UI. Add temporary structured logging at each stage so the failure point is unambiguous, and report to me what you find before you fix it.

Check these known Expo Go failure modes specifically, in order of likelihood:

1. **Backend URL unreachable from the phone.** In Expo Go the app runs on my physical iPhone, so any `localhost` / `127.0.0.1` / Replit-internal backend URL will fail. The app must call the backend's publicly reachable URL. Verify which URL the STT upload actually uses vs. what the working features use.
2. **iOS audio mode not set for recording.** Recording on iOS requires `Audio.setAudioModeAsync({ allowsRecordingIOS: true, playsInSilentModeIOS: true })` before starting, and it should be reset after stopping so playback isn't stuck in receiver mode.
3. **Permission flow.** Confirm `Audio.requestPermissionsAsync()` is awaited and its result is checked before recording, with a clear user-facing message when denied. (`NSMicrophoneUsageDescription` in app config doesn't apply inside Expo Go, but note it anyway for our future native builds.)
4. **Recording format mismatch.** Expo Go on iOS records `.m4a`/`.caf` depending on the preset. Confirm the backend's transcription endpoint accepts the exact container/codec being produced. If not, set explicit `Recording` options (e.g. `Audio.RecordingOptionsPresets.HIGH_QUALITY` or a custom preset) to produce a format the backend accepts — change the client options rather than adding server-side transcoding.
5. **Upload construction.** React Native `FormData` file parts need `{ uri, name, type }` with a correct MIME type, and no manually set `Content-Type` header (the boundary must be auto-generated). Verify the file at the recorded URI is non-empty before upload.
6. **expo-av deprecation quirks on SDK 54.** We're on Expo SDK 54 where `expo-av` is deprecated in favor of `expo-audio`. If the root cause is an SDK-54 `expo-av` recording bug, migrating just the recording code to `expo-audio` is acceptable — but only if it stays fully Expo Go-compatible, and migrate only the STT recording path, nothing else.
